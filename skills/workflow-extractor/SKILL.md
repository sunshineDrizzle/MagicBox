# 从真实工作中提炼可复用 Skill

目标：把**已经发生的工作**还原成**独立自洽**的 skill 包——即使原工作路径被删除，
新的 agent 也能凭 skill 包 + 外部输入（源数据、凭据、初始设置等）完成同一目标。

## 输入

- **工作路径**：一个或多个目录/文件
- **工作目标**：可选，用户 1–3 句描述
- **产出路径**：可选；默认当前会话工作目录，用户显式指定时以用户为准

### 用户未提供工作路径时

不要自行猜测。给出以下选项让用户选：

1. **当前会话工作目录**（同时展示其绝对路径，供用户确认）
2. **用户手动填写**一个或多个路径
3. **从最近会话/历史推断候选**：列出可能的目录，让用户确认

选定后，把最终路径清单复述给用户确认，再开始勘察。

## 强制交互门（每次执行都必须重新完成）

以下三项**每次执行都要重新确认**，不得复用历史决定，也不得用默认值代替：

1. **工作路径**：用户确认要提炼的路径（未提供时给出选项）
2. **超阈值证据**：会话/日志超过第 3 步阈值时，让用户选择
   全部纳入 / 筛选后纳入 / 不纳入；**默认行为是停下来问，不是默认不纳入**
3. **输入样本路径**：输入为文件/目录且工作路径中没有真实样本时，
   从证据推断候选，让用户确认或另填；用户不提供时标注「未经样本验证」

**在进入第 6 步构建之前，必须已在对话中记录以下内容**（并纳入 A–F 报告）：

- 工作路径：`<路径>`（用户确认）
- 超阈值证据：`<全部 / 筛选 / 不纳入>`（用户确认）
- 输入样本：`<路径 / 未提供>`（用户确认）

**缺少任一项记录，不得进入构建。**

若执行 agent 没有专用交互工具：输出编号选项并停止，等待用户回复；
不得自行选择或跳过。

## 核心原则

- **Evidence-first**：只写证据支持的内容；推测必须显式标注
- **Reuse-first**：优先调用**已经验证的脚本、模块和工具**，不为创建 skill 而重写；
  复制进包是为了自洽，不是为了改造或重写
- **Deterministic-by-default**：重复性强、需要严格保证正确性的操作交给确定性代码；
  agent 只负责流程编排、参数选择、异常诊断和必要的人工交互
- **No invented rules**：尚未明确的业务规则不得推断或固化为自动决策；
  标注为待确认，交人工决定
- **不泄露敏感信息**：产出包不得包含真实数据、个人可识别信息、健康信息、
  凭据或内网地址；样例只用合成或充分脱敏数据
- **Self-contained**：产出的 skill 包独立自洽，不依赖原工作路径继续存在
- **Validation-first**：验证分级，不夸大完成度
- **默认只读 / dry-run**：全量执行、覆盖产物、外部写入必须获得授权
- **跨 agent**：不依赖任何 agent 专有机制，不把特定 agent 当作前提
- **不固定路径**：所有路径通过参数/配置解析，不写死；相对路径要说明基准

## 第 1 步：勘察路径与证据源

对每个路径只做**轻量勘察**，不读正文。检查以下证据源：

- **代码与结构**：目录布局、入口脚本、依赖与配置
- **文档与约定**：README、SOP、数据字典、技术文档、操作规范
- **版本历史**：commit、PR、Issue、变更记录
- **运行证据**：日志、错误记录、修复过程、最终产出
- **历史上下文**：会话记录、任务摘要、持久化 memory
- **已有 skill 与工具**（第 5 步会系统查找）

同时记录路径角色（数据源 / 代码 / 文档 / 日志 / 产物 / 混合）与规模
（文件数、总大小、时间范围）。**多个路径时说明它们的关系**
（如 输入 → 代码 → 产物 → 日志），不要当成互不相关的目录。
会话历史按**执行 agent 自己的格式**探测（见 `references/EVIDENCE.md`），
探测不到就标记「不可用」，不要假设。

勘察时判断工作类型：若涉及数据清洗、转换、标准化、整合、QC、导出或发布，
后续启用 `references/DATA_GOVERNANCE.md` 的扩展要求。

输出一份简短清单，告诉用户你看到了什么。

## 第 2 步：确定工作目标

按以下顺序确定，前一项不能可靠判断时才看下一项：

1. 工作路径下的正式文档（README、SOP、规范、数据字典）
2. 代码与产物的结构（入口脚本、输入输出、目录布局）
3. **用户的 1–3 句描述**
4. 会话历史中的背景信息（需先按第 3 步判断是否纳入）

文档用于确定**意图与约定**，但其中的**环境限制和操作断言需要验证**：
「只在某平台可用」「必须有某账户」「直接运行某命令才能启动」这类说法，
可能已经过时、针对作者自己的环境，或描述的是人类操作路径而非自动化路径。
执行细节以代码和实际运行为准；与文档冲突时记录差异，不盲从也不擅自否定。

仍无法确定时，直接问用户，只问最少的几个问题：

- 这项工作要达成什么？
- 哪些路径分别是输入、代码、输出、日志？
- 有没有已知规范或验收标准？

用户描述标注为「用户陈述」，需与文档/代码交叉验证。

## 第 3 步：证据预算与用户决策

先只取元数据：文件数、大小、行数、时间范围。

**证据预算** = 允许读入上下文的证据上限，默认：

- 文本总量 ≤ 5 MB，或 ≤ 300 条消息
- 超出部分只做抽样或摘要，不全文读入

**触发用户决策的阈值**（任一满足）：

| 证据 | 阈值 |
|---|---|
| 会话记录 | 单文件 > 5 MB，或总计 > 20 MB，或 > 500 条消息 |
| 日志 | 单文件 > 50 MB，或总计 > 20 万行 |
| 任意证据 | 预计需读入 > 5 MB 文本 |

超过阈值时，列出规模并让用户三选一：**全部纳入 / 按关键词或时间筛选 / 不纳入**。
**默认不纳入**。阈值可按执行 agent 的上下文能力调整，但必须在报告中写明实际采用的预算。

## 第 4 步：证据分级与工作流还原

| 级别 | 证据 | 回答什么 |
|---|---|---|
| 1 | 正式文档 | 意图、约定、边界（「应该怎么做」） |
| 2 | 代码、配置、产物 | 实际执行细节（「真正做了什么」） |
| 3 | 日志、报错、版本历史 | 验证与异常（「实际发生了什么」） |
| 4 | 会话历史、memory | 背景与经验（「为什么这样做」） |

规则：

- **文档定意图，代码定细节**
- 冲突不自行裁决：记录差异，在报告中列为待确认
- 还原内容包括：
  - 输入形式（在下文单独展开）
  - 执行步骤，以及使用的脚本、工具、依赖与参数
  - 步骤顺序与依赖关系（哪些可并行、哪些必须串行）
  - 业务规则与判断依据
  - 数据或输入异常的处理方法（缺失、重复、异常值、冲突、不完整）
  - **实际发生过的问题 → 诊断过程 → 修复方案**
  - **已自动化的操作 vs 仍需人工判断的部分**
  - 产物、结构或数据契约、质量要求与下游用途
  - 完成信号
- 每条关键描述尽量附证据位置（文件路径、代码位置、命令、日志行、commit/PR）
- 历史不可访问或无法验证的部分，明确标注缺口，并用可验证的代码、配置、文档
  或日志作为替代证据；仍无法还原的写入 A–F 报告的 E 项

**输入形式必须单独分析并记录，且以执行入口为准**。

先看**执行入口（driver）实际如何获取输入**——这是输入形式的权威来源：

- 从哪里取：命令行参数、配置文件、环境变量、固定路径、stdin、目录扫描、网络请求
- 接受什么形态：文件集合 / 表格数据 / 代码与构建 / 服务 API / 配置 / 消息 / 人工输入
- 前置检查：入口自己校验什么、缺失或格式不符时如何报错

再看输入本身：来源、规模、组织方式、命名与编码约定、正常与异常形态。
**不同工作的输入形态差异很大**：表格关注 schema/单位/主键，代码关注版本/依赖，
服务关注协议/鉴权，人工输入关注字段/确认点。按实际形态记录，不要套用表格模板。

**若输入是文件/目录，但工作路径中没有真实样本，向用户索取一个代表性路径**：

- **先从证据推断候选**：执行入口的参数默认值、**配置文件**（JSON/YAML/TOML 等）、
  代码中的路径常量、文档示例、日志中的实际路径。列出 1–3 个候选并标注来源，
  让用户确认或另填；推断值只是候选，必须验证是否存在
- 只做只读、抽样检查（遵循第 3 步的证据预算），记录真实格式、编码、空值、
  异常形态、隐藏列等代码里看不出来的信息
- 不把输入数据写入 skill 包；含敏感信息时只记录结构特征
- 用户不提供时，明确标注「输入形式仅由代码推导，未经真实样本验证」
- **无论用户是否提供样本，执行入口与代码推导出的契约仍是主要依据**；
  样本用于验证和补充，不替代代码事实

偏差适配的终点是**整理成执行入口能接受的形式**：能确定语义的映射与转换
（命名、格式、单位、缺非必需项）可自动处理；语义不明的（缺必需项、新编码、
标识或关联冲突、输入形态变化）必须停止询问。

分析结果写入 skill 包：SKILL.md 的 Inputs 章节；复杂时按本 skill 的
`references/INPUT_CONTRACT.md` 模板填写。

还原过程中维护一份工作笔记。最终沉淀到 skill 包的 `references/`：
证据索引进 `EVIDENCE_INDEX.md`，实际遇到的问题与修复进 `TROUBLESHOOTING.md`。

## 第 5 步：查找已有 skill 与可复用单元

先查找是否已有覆盖这项工作的 skill（按 description 匹配，不只看名字）。
若存在：**refine，不要重写**——验证其声明、修正错误、补齐缺口，保留可用部分和原名称。
若它位于某个 agent 的专有目录（如 `.claude/skills/`），不要直接改造它：
产出一个独立的跨 agent 包，并在 A–F 报告中说明两者的关系与取舍。

再识别值得沉淀的流程。优先选择满足以下条件的：

1. 已实际执行，最好**至少重复两次**；或有明确证据表明未来会持续重复
2. 输入、执行步骤、输出相对稳定
3. 含领域知识、复杂业务规则或易错点
4. 能显著降低后续 agent 的探索成本
5. 尚未被现有 skill / 工具充分覆盖

常见的可复用单元类型：

- 新批次 / 新输入的接入与校验
- 格式、结构或语义的转换与标准化
- 标识、实体或事件的关联
- 质量检测与异常发现
- 结果验证与发布
- 常见错误的诊断与修复

一次性探索、未验证的工作不要强行封装。多个步骤共同构成稳定且完整的流程时，
组织为一个 skill，不必机械拆分。

## 第 6 步：构建独立自洽的 skill 包

产出目录按前述规则（默认当前会话工作目录，用户指定优先）。skill 包结构：

```
<skill-name>/
├── SKILL.md          # 开放 Agent Skills 规范；跨 agent
├── scripts/          # driver + 从工作路径纳入的脚本
├── references/       # 契约、异常处理、证据索引
└── assets/           # 按需：模板、schema、脱敏样例、校验基线
```

### 自洽性要求

- 把工作路径下**需要复用的脚本、配置模板、schema、校验基线原样复制进包内**；
  必须修改时记录原因与改动点
- 包内不得依赖原工作路径继续存在
- 外部依赖（源数据、凭据、外部服务）通过参数/配置注入，并在 SKILL.md 写明获取方式
- 复制第三方脚本时保留来源与许可证说明

### 敏感信息约束（所有产出包适用）

以下内容**不得进入 skill 包**（包括 SKILL.md、scripts、references、assets，
以及执行后生成的 run_manifest.json）：

- 真实数据样本（除非已充分脱敏，且脱敏方式可审计）
- 个人可识别信息：姓名、身份证号、手机号、邮箱、地址、患者/受试者 ID、
  真实业务主键或其他直接标识符
- 健康、基因、影像等个人敏感信息
- 凭据：密码、token、API key、私钥、连接字符串
- 内网地址、主机名、内部域名、内部系统路径
- 第三方脚本中硬编码的密钥或账号

要求：

- `assets/` 只放合成数据或脱敏样例；脱敏需移除或替换直接标识符
- 报告中引用数据时用统计量或占位符，不贴真实记录
- 无法确认脱敏是否充分时，停止并询问用户，不要猜测
- **违反本约束的产出包不得交付**

### SKILL.md 要求

frontmatter：`name` 用 kebab-case；`description` 写清「做什么 + 何时用 + 用户可能的说法」。

正文至少包含以下章节：

1. **Name & Description**：用途、触发条件、适用范围、**不适用边界**
2. **Inputs & Preconditions**：输入形态与契约（按实际形态记录，不预设为表格）、
   **参数表与依赖表**（见下）、运行环境与权限、前置检查、输入偏差的适配规则
3. **Workflow**：可重复的操作步骤、每步使用的脚本/工具/参数、关键判断规则及依据、
   agent 决策与确定性代码的职责划分、异常处理与终止条件
4. **Outputs**：产出物、报告、异常记录、可追溯证据
5. **Validation**：成功标准、失败条件、需要人工确认的情况
6. **Examples**：至少一个成功案例、一个异常案例、可复现的调用示例

其他要求：

- **保持简短**，细节放 `references/`，执行入口指向 `scripts/`
- 路径解析：参数 > 配置 > 默认，不写死；说明相对路径的基准；
  **同一配置项只有一个权威来源**，不在多处重复定义
- 不依赖特定 agent 机制；提及其他 agent 时标注为示例
- red flags、driver 形态、通用停止条件见 `references/QUALITY.md`
- 数据治理类工作额外增加 Data Contract 与 Validation & Quality Gates 章节，
  见 `references/DATA_GOVERNANCE.md`

### 参数与依赖清单

产出包必须包含参数表与依赖表（写在 SKILL.md 的 Inputs 章节；复杂时放 `references/`）。

**参数表**：

| 参数 | 默认 | 必需 | 影响 | 覆盖方式 |
|---|---|---|---|---|

默认值分三类：

- **环境无关**（输出文件名、超时、日志级别）：可以给明确默认值
- **环境相关**（输入路径、凭据、服务地址）：**不得给真实默认值**，用 `null` 或占位符
- **依赖**：见下表

**依赖表**：

| 依赖 | 必需性 | 兼容范围 | 实测版本 | 缺失时的行为 |
|---|---|---|---|---|

规则：

- 兼容范围必须有依据（锁文件、依赖声明、实际测试）；**实测版本不是约束**
- 明确写：优先使用环境中已满足范围的版本，不要为了贴合记录而安装、降级或改动环境
- 可选依赖标注降级行为；缺失时先报告，安装需用户授权
- 不得编造版本范围或依赖关系

### driver 是交付物

至少有一个可执行入口，或「人工步骤 + 每步校验命令」。完成信号不要求退出码，
按工作类型选择：输出文件、记录数/缺失率/唯一性、日志关键字、断言查询、
服务健康检查、人工确认。

### 配置前置与非交互执行

driver 应支持：

- `--config <file>`：从配置文件读取参数
- `--yes`：跳过常规确认
- `--dry-run`：只打印计划与配置摘要，不执行

启动时打印最终配置摘要（输入、输出、关键参数、模式）。只对高风险项确认：
覆盖产物、删除、外部写入、全量执行；缺失必填项时才交互。

**免交互只跳过常规确认，不跳过异常处理**：冲突、缺列、独立校验失败、输入缺失
仍必须中断。这与提炼阶段的「强制交互门」是两回事。

### run_manifest.json

每次实际执行后在输出目录写 `run_manifest.json`（与产物同级）：

```json
{
  "skill": "", "started_at": "", "finished_at": "", "duration_sec": 0,
  "inputs": {"paths": [], "counts": {}},
  "outputs": {"paths": [], "counts": {}, "sha256": {}},
  "params": {},
  "dependencies": {"name": {"required": true, "range": "", "observed": ""}},
  "result": {"exit_code": 0, "verified": true, "warnings": []}
}
```

只记录路径、计数、版本、结果；不记录凭据或敏感内容。不生成 `run_log.md`。

### README（默认生成）

每个产出包默认包含面向人的 `README.md`：

- 用途
- 最小调用示例
- 参数与依赖摘要
- 输出
- 出问题看哪里

边界：

- 不替代 SKILL.md；运行时以 SKILL.md 为准
- 不写 agent 执行步骤、完成信号、内部规则
- 不写环境特定绝对路径
- 用户明确不需要时才跳过

## 第 7 步：在隔离环境中验证 skill 包

**验证对象是 skill 包本身，不是原工作路径。**

**隔离测试**：把 skill 包复制到临时目录，只提供最小输入（样例数据/测试凭据），
从零按 SKILL.md 执行一遍；原工作路径的其他内容不参与。

最小输入优先用脱敏样例或合成数据；无法构造时只做静态验证，并在报告中明确
标注「未做冒烟/全量验证」及原因。不得用真实敏感数据替代。

| 级别 | 内容 | 默认 |
|---|---|---|
| 静态 | 包内引用存在、命令可解析、依赖声明完整 | ✓ |
| 冒烟 | 最小输入跑通主路径 | ✓ |
| 全量 | 完整数据与流程；先估算耗时、资源、副作用 | 需批准 |
| 未验证 | 环境不具备；写明原因 | 标注 |

验证重点（逐条检查）：

1. 一个不了解历史的新 agent，能否只按 SKILL.md 理解并执行任务
2. 包内引用的文件、脚本、依赖、参数是否真实存在
3. 输入、输出、执行边界是否清晰
4. 异常输入能否被识别并安全停止
5. 能否复现已有工作的关键结果（有产物则做比对）
6. 是否与现有 skill 或工具重复（交付前再次确认；重复时应 refine，而不是新建）
7. 敏感信息扫描是否通过（包内文件、assets、日志、run_manifest.json）

另需：

- 每步记录验证级别（`full` / `smoke` / `static` / `unverified`）
- **记录实际测试结果；未执行的测试必须明确说明，不得宣称已通过**

优先级：**有历史产物时先做产物比对**，不必重跑。最终对照文末自检清单逐项确认。

## 第 8 步：A–F 交付报告

在对话中输出（不放进 skill 包）。**开头必须先列出强制交互门的决策记录**：

- 工作路径：`<路径>`（用户确认）
- 超阈值证据：`<全部 / 筛选 / 不纳入>`（用户确认）
- 输入样本：`<路径 / 未提供>`（用户确认）

然后是：

- **A. 已有工作回顾**：原流程、证据来源、缺口
- **B. Skill 交付**：名称、路径、适用场景、核心能力、调用方式
- **C. 复用收益**：可复用步骤、仍需人工的部分
- **D. 验证结果**：各步骤的验证级别；实际跑过的命令；未执行及原因；
  **敏感信息扫描结果**
- **E. 尚未解决的问题**：缺失规则/证据、未裁决的冲突、需确认事项
- **F. 下一步建议**：需要完善的能力、适合公共化的部分
